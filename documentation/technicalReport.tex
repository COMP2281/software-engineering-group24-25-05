\section{Introduction}

\subsection{Main Motivation and Goals}

\noindent Shadow Operative is a Project which gracefully integrates IBM Skills Build in order to provide users a more fun and interactive way of learning from the IBM Courses. This goal is approached by incorporating fun gameplay mechanics to balance the amount of learning material the user encounters. The balancing of educational content with gameplay is seamless, this is supported by having an AI create a compelling and realistic environment akin to the game inspiration CounterSpy. \\

\noindent The project benefits individuals who currently learn using IBM Skills Build, including self-learners and educational institutions looking for interactive tools to complement their curriculum. Gamifying the learning process can further the audience and effectiveness of the IBM Skills Build course with younger users in mind. \\

\noindent The client for this project is IBM, represented by John McManara, who leads the IBM UK University Programs and serves as an IBM Master Inventor. IBM’s overarching goal is to increase the engagement of Skills Build content. This project aligns with IBM’s strategic aim to integrate cutting-edge solutions into its educational offerings.

\subsection{Instructions on Installation and Setup}

\noindent The game is accessible through an online platform. Users can play the game via their web browser without needing downloads or additional installations. \\

\noindent Instructions to access the game:

\begin{enumerate}
    \item Open a web browser.
    \item Navigate to the game’s hosting website via \textbf{https://williammorgan73.itch.io/shadow-operative}
    \item Click on the level that you wish to play.
    \item Follow the in-game instructions to begin playing.
\end{enumerate}

\noindent For optimal performance, it is recommended to use a modern web browser with a stable internet connection. If users encounter any issues, they should refer to section 3.4 of this technical report.

\section{Technical Development}

\subsection{Source Materials}

\subsubsection{Educational Foundations}

\noindent A key foundation of our project is the IBM SkillsBuild platform, which was provided by the client as the primary source of educational content. This platform offers structured learning materials in areas such as AI, Cybersecurity, and Data Analytics. The courses and digital badges from Skills Build serve as the basis for the in-game question bank, ensuring that the educational content aligns with industry-relevant skills. By embedding these challenges into the gameplay, Shadow Operative merges interactive learning with entertainment, allowing for knowledge retention and engagement. \\

\noindent To enhance the educational experience, the game integrates adaptive learning technologies. The client emphasised the need for a dynamic difficulty system, ensuring that players receive challenges suited to their progress. To achieve this, the game employs player performance tracking, where the difficulty of questions adjusts dynamically based on previous answers. If a player struggles with a topic, the game introduces more foundational questions before progressing to advanced ones, optimising both engagement and comprehension. This approach is informed by established educational models, such as Bloom’s Taxonomy, which structures learning objectives based on cognitive complexity. \\

\noindent The client provided courses outlining key learning objectives and industry-relevant topics, which helped refine the question bank and ensure that the educational content met their expectations.

\subsubsection{Game Design Influences}

\noindent Shadow Operative draws inspiration from existing games that emphasise stealth and engagement to refine its structure and mechanics. The client specifically provided CounterSpy as the primary reference for the game's setting and design. This Cold War-era stealth game directly influenced Shadow Operative’s visual style, mechanics, and overall atmosphere. However, unlike CounterSpy, Shadow Operative integrates educational elements into its core gameplay, transforming the espionage theme into a learning-driven experience. \\

\noindent Additional game design influences include:

\begin{itemize}
    \item This War of Mine provides insights into stealth mechanics, art style, and thematic depth; Shadow Operative adapts these elements for an educational experience suitable for younger audiences.
    \item Kahoot! provides a model for question-based engagement, while Shadow Operative enhances it by embedding learning challenges within an immersive storyline instead of standalone quizzes.
\end{itemize}

\subsubsection{Technical Framework}

\noindent The game is developed using Unity, leveraging its 2D engine for efficient and seamless gameplay. The development follows best practices in game design, incorporating principles from Karl Kapp’s The Gamification of Learning and Instruction to enhance engagement and motivation. \\

\noindent Additionally, accessibility and user engagement are key priorities, with customisable controls ensuring inclusivity for different players. Users can remap key bindings and adjust input settings to suit their preferences, allowing for greater flexibility in gameplay. This feature enhances accessibility for players with different control preferences and ensures a comfortable experience across various input methods. \\

\noindent By combining client-provided educational content, industry-aligned learning objectives, established game mechanics, and adaptive AI-driven learning, Shadow Operative offers a unique approach to skill development. The integration of these diverse source materials ensures an engaging, inclusive, and effective learning experience for all players.

\subsection{System Architecture}

\subsubsection{Technologies}

\begin{enumerate}
    \item \textbf{Unity Engine}
    \begin{itemize}
        \item \textbf{Unity Editor}: development environment for creating, editing and managing projects and their scenes, assets and scripts; also has the ability to debug
        \item \textbf{Unity UI}: framework for creating user interfaces (buttons, panels, text, etc.); it is event driven
        \item \textbf{Asset Bundles}: framework for packaging and loading assets dynamically, also used to import custom libraries such as UI and shaders
        \item \textbf{Physics Engine}: default physics engine in Unity, primarily used for character controllers and collision detection
        \item \textbf{Lighting Engine}: default lighting \textbf{GameObjects} are used to create the "atmosphere" of the game
        \item \textbf{Sprite Sheet}: used for creating animations for dynamic \textbf{GameObjects}; Unity supports the conversion of such a sheet into usable sprites for animation
        \item \textbf{Sprite Palette}: Unity's built-in software for creating static level assets, such as environment
    \end{itemize}
    \item \textbf{Storage}
    \begin{itemize}
        \item \textbf{JSON}: file format chosen for the storage of the \textbf{IBM SkillsBuild} question bank, achieved through the \textbf{JsonUtility} class provided by Unity's library
        \item \textbf{PlayerPrefs}: used for saving the current status of the player (position, levels completed, questions answered), achieved through the \textbf{PlayerPrefs} class which is provided by Unity's library
    \end{itemize}
    \item \textbf{Programming Languages}
    \begin{itemize}
        \item \textbf{C\#}: language used for writing scripts for \textbf{GameObjects} in the Unity Engine which dictate their behaviour
    \end{itemize}
    \item \textbf{Version Control System}
    \begin{itemize}
        \item \textbf{git}: standard across many other software development projects
    \end{itemize}
\end{enumerate}

\subsubsection{Platforms}

\begin{enumerate}
    \item \textbf{Operating Systems}
    \begin{itemize}
        \item \textbf{Windows 11}: used for development and testing
        \item \textbf{Linux}, \textbf{MacOS} and \textbf{ChromeOS}: used for testing; may be used for development if a developer chooses to do so / has a preference for the operating system

\subsubsection{Software Development Process}

\noindent The chosen software development life cycle is the \textbf{Incremental Model} which divides the project into smaller, manageable portions (increments). Each increment builds upon the previous one. \\

\noindent \textbf{Gradual Progress:} Our game comprises multiple components, including core mechanics such as movement, enemy AI,  and IBM Skills Build badge questions. Using the Incremental Model, we can develop each component sequentially, starting with the foundational mechanics. \\

\noindent \textbf{Iterative Feedback and Testing:} After completing each increment, we can conduct testing and gather client or player feedback. This ensures each feature works as intended and aligns with the project goals before integrating it into the overall game. \\

\noindent \textbf{Risk Management:} By addressing straightforward features early in the development process, the Incremental Model reduces risk and ensures a consistent development pace. This strategy allows us to allocate more time and resources to resolving challenges posed by complex features. \\

\noindent \textbf{Flexibility for Changes:} Given the possibility of evolving client requirements or necessary adjustments, the Incremental Model minimizes disruption. Changes can be accommodated without requiring significant rework, as only specific increments need updating, preserving the integrity of prior developments. \\

\noindent \textbf{Early Player Engagement:} The model allows us to release a playable version of the game before full completion. Early releases enable us to collect valuable feedback from players and the client, refining the game’s direction and functionality based on real-world input. \\

\noindent \textbf{Adaptability to a Small Team:} With a team of seven, the Incremental Model facilitates efficient workload distribution. Team members can focus on specific tasks within each increment, ensuring all participants are engaged and progress is clearly tracked. \\

\subsubsection{Behaviour Driven Development}

\noindent The Incremental Model and BDD complement each other effectively in the software development process. \\

\noindent Each increment was developed, tested and reviewed. This has aligned well with BDD due to each increment representing the implementation of a behavioural requirement, which in the testing period has been reviewed by the relevant stakeholders. \\

\noindent Due to the low risk and flexibility of the chosen software development process it has allowed us to continually refine and evolve the requirements based on testing results and stakeholder feedback. \\

\noindent BDD has played a key role in the development process by allowing the team to designate increments as the implementation of a requirement and to have a clear goal in mind, and has facilitated good collaboration between the development team and the stakeholders. \\

\noindent Due to the rigorous testing required by BDD it played a significant role in the quality assurance process; our project had to abide by the strict requierements.

\subsubsection{Applied Design Principles}

\noindent \textbf{Open / Closed Principle}: modules such as the \textbf{SkillsBuild} implementation and the \textbf{Enemy} class implementation are generic, they can be expanded upon through inheritance without having to modify the base class. \\

\noindent \textbf{Single Responsibility Principle}: has been applied to concepts such as the \textbf{LevelManager}, \textbf{LevelCompleter}, \textbf{LevelEndTrigger}, \textbf{SkillsBuildDataLoader} and the \textbf{PlayerViewcone}. They have only one purpose, offer consistent interaction APIs such that internal changes do not affect outside modules. \\

\noindent \textbf{Interface Segregation Principle}: this is the de facto standard in any Unity project, with the way entities and \textbf{GameObject}s are setup in the \textbf{Unity Editor} they only depend on each other if explicitly stated by the developer. \\

\noindent \textbf{DRY}: unintentionally applied due to the project scale being small and the ratio of code to assets is small \\

\noindent \textbf{KISS}: with the aforementioned point made, we have relied heavily on pre-existing assets (including the vast library offered by the Unity Engine) in order to keep complexity at minimum, the thought being that if the library offers the functionality there is no reason to re-implement it

\subsubsection{Applied Design Patterns}

\noindent \textbf{Component Pattern}: obliged to use it due to Unity's architecture, all of the modules inherit from the \textbf{MonoBehaviour} base class which can be attached to \textbf{GameObject}s in the Unity Editor. \\

\noindent \textbf{Singleton Pattern}: used for event emitters such as \textbf{InputManager}, \textbf{DialogueManager}, \textbf{AudioSettingsManager}, \textbf{LevelManager}, by having a single easily accessible instance the complexity has been reduced; other modules do not have to keep a reference towards such instances. \\

\noindent \textbf{State Pattern}: this pattern has been applied when designing the non-playable characters (enemies), when they have detected the player their state changes from patrolling to chasing and start following the player. \\

\noindent \textbf{Event Aggregator Pattern}: when an enemy catches the player it will trigger the \textbf{SkillsBuild} functionality. \\

\noindent \textbf{Observer Pattern}: the \textbf{LevelEndTrigger} class observes a \textbf{GameObject} such as a Console in order to decide whether to trigger the end of the level.
